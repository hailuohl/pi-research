# Codex 持续推进入口：研舟π通用科研工作台

版本：1.0；日期：2026-10-21。用途：让新 Codex 会话在真实当前代码上接续本设计，逐批交付可验证的功能。

产品是通用科研工具。此目录管理**开发项目的工作**；它不替代产品内的 ResearchBrief、Task、Campaign 或 Pi 执行状态。

## 1. 第一次接手

目标仓库：`D:\项目\pi research\pi-research`。在实际仓库根执行；换电脑或克隆后由用户指定对应位置，不能因旧绝对路径不存在而创建一份空项目。

按以下顺序阅读：

1. 仓库根及适用子目录的 AGENTS.md，确认当前授权、文件归属、模型与验证规则。
2. [STATE.json](STATE.json)：唯一的开发任务进度；首先看 nextTaskId、activeBatch、blockers。
3. [HANDOFF.md](HANDOFF.md)：本次接续的必要上下文和具体下一步。
4. [BASELINE.json](BASELINE.json)：编写方案时的已核实快照；它是对照证据，不是要求回退到该版本。
5. [详细设计](../../superpowers/specs/2026-10-21-general-research-design.md)：首次完整阅读；续接时阅读当前批次及不变量。
6. [执行计划](../../superpowers/plans/2026-10-21-general-research-plan.md)、[VALIDATION.md](VALIDATION.md)、[DECISIONS.md](DECISIONS.md)：确定当前批次的范围、完成条件和已定取舍。

本方案最初交付时所有产品任务为 not_started。文档已经写好不能作为代码实现、产品测试、用户启动实施或部署的证据。

## 2. 可直接交给 Codex 的启动指令

下列文本是供用户发送的实施指令示例。文件自身不会自动给 Codex 增加权限。

```text
请在 D:\项目\pi research\pi-research 持续实施“通用科研工作台”方案。

先读取仓库 AGENTS.md 和 docs/codex/general-research/START_HERE.md，
再按 STATE.json、HANDOFF.md、详细设计和执行计划，从 GR00 开始。

我授权实施该方案内的后端、契约、测试，以及必要的前端入口与交互调整；
就本方案涉及的“概览、资料与成果、比较表、研究上下文、行动摘要和成果编辑”，
恢复此前暂缓的前端工作。不要扩大为全面视觉重设计。

保持通用科研定位，保留已有工作树改动，复用现有 Pi、权限、证据、执行与成果机制。
每批只推进一条可验收的用户流程，遵循根 AGENTS 的分工、验证和私密仓库交付规则。
记录实际完成、失败、未运行和阻塞证据；不能用规划完成或 stub 测试代替功能完成。

在已授权范围内连续推进，不必每批重新询问。遇到阻塞时先完成不依赖它的任务；
只有缺失的决定、权限或环境确实阻断全部下一步时再说明具体原因。
每批更新 STATE.json 和 HANDOFF.md；会话结束前留下准确下一步。
完成本方案后停止扩展范围，汇报已完成能力、验证证据及剩余限制。
```

若实施已经开始，可用更短的接续指令：

```text
继续 D:\项目\pi research\pi-research 的通用科研工作台方案。
读取 AGENTS.md、docs/codex/general-research/START_HERE.md、STATE.json 和 HANDOFF.md。
先核实当前代码及上次进程/提交状态，再从第一个满足依赖的未完成批次继续。
沿用本会话已有授权；不要重新做已有效完成的检查，也不要覆盖其他在途改动。
```

## 3. 每次会话的推进算法

### 3.1 恢复事实

检查 HEAD、分支、未提交差异、暂存区、远端对应关系，以及与当前批次有关的活跃进程/代理。读取 STATE.revision；如已有实施者占用同一批次，先核对其状态，不能因观察超时重复启动。

将当前代码与 BASELINE 对比。不同是需要理解的变化，不是失败。存在大量旧改动时，纯 HEAD 的 worktree 不包含它们；需要隔离则制作含本批必要当前改动的工作副本，并记录源文件摘要。

上次标为 in_progress 而执行者已结束：读取实际差异、日志、构建结果和提交，再决定转入验证、继续实现或记录阻塞。不能直接清空状态或重做全部内容。

### 3.2 选择一批

按 STATE.taskOrder 查找依赖完成的未完成任务。先处理直接影响当前任务的 R01/R02；其余条件修复不阻止只读目录等独立任务。不得跳过关键验收将依赖伪装成完成。

开始前把 activeBatch 写清：taskId、目标、3–5 条验收 ID、基线、文件所有权、允许操作、共享资源、实施者与复核要求。通常一次只激活一个批次。

默认顺序为 GR00 → GR01 → GR02 → GR03 → GR04 → GR05 → GR06 → GR07 → GR08 → GR09 → GR10。存在阻塞时可按依赖图转向 GR05、GR08 等独立项。GR09 中已有的手工表格/成果复用可提前验证；GR09 整批 done 仍需满足其全部验收及依赖。

### 3.3 实施和验证

先锁定行为差距，再添加能暴露该差距的测试和最小实现。新服务必须接入原 operation schemas、权限、来源核验、生命周期、UI 及适用的备份恢复；单独新增一个类不算用户流程完成。

开发阶段只运行相关检查。集成后按 V-GATE 做必要全量回归、干净构建和独立复核。真实浏览器检查针对本批流程；涉及真实 Pi、Docker、SSH 或外部服务时，只验证实际授权和具备环境的路径。缺关键环境记 blocked；stub、skip 和环境未就绪不能记 pass。

查出阻断后只修本批必要问题。修复改变公共契约或使旧证据失效时补相应检查；否则复用同一快照仍有效的证据。没有新证据的重复失败应转向补上下文/环境或定向诊断，不盲目重跑和换模型。

### 3.4 收口和接续

独立复核锚定当前代码快照。修复后复查受影响部分，明确阻断已解决；非阻断建议进入后续事项，不能无限扩大当前批次。

只暂存本批明确文件/区块。按根 AGENTS 提交并推送已核实的私密仓库对应分支，随后核对远端包含本次提交。不得覆盖其他人的 index 内容、使用全量暂存、强推、重置或混入运行数据。

STATE 的 implementationCommit 记录**产品代码提交**，不要求指向包含该字段的文档提交，避免提交 SHA 自引用。可先提交并推送代码，再用一次精简的交接文档提交持久化验证、代码 SHA 和远端结果；纯交接更新只做文档校验，不重跑无关产品回归。每个正式提交仍按根规则推送。最终同步失败保留本地成果，明确 remoteStatus=failed/pending。

更新 STATE 和 HANDOFF，选择下一任务后继续；全计划完成、全部可推进任务被阻塞、用户要求暂停或会话即将结束时留下交接。

## 4. 状态、所有权和证据规则

STATE.json 是唯一任务进度源。执行计划复选框是步骤描述，不另存第二份进度。HANDOFF 仅保留定位下一步所需内容，不复制所有日志。

| 状态 | 精确定义 | 允许的下一步 |
|---|---|---|
| not_started | 未开始该批产品实施 | 满足依赖后设 in_progress |
| in_progress | 已明确所有权，正在实现或修正 | verify_pending / blocked |
| verify_pending | 实现已集成，必要验收尚未全部完成 | review_pending / in_progress / blocked |
| review_pending | 验收证据齐备，等待或正在独立复核 | done / in_progress / blocked |
| blocked | 当前缺口阻止本批满足验收，必须有解除条件 | 条件解除后回到相应状态 |
| done | 3–5条验收通过、必要验证有效、独立复核无阻断 | 发生新回归时显式重新打开 |
| deferred | 经用户或明确计划范围调整延期 | 重新批准范围后启动；不能等同完成 |
| not_applicable | 条件任务经当前证据确证不适用 | 仅用于R01/R02；核心GR任务不使用 |

done 与 Git 交付是独立维度：验证已通过但推送失败，任务可 done，整体 delivery 必须标 incomplete；最后汇报必须说明远端未同步。没有完成全体 GR 核心任务，不得宣称整个方案实施完成。

remoteStatus统一为not_attempted/pending/synced/failed；delivery.overallStatus统一为not_started/in_progress/incomplete/complete。产品完成且本批提交同步成功，整体才可complete；未同步不抹掉已验证的功能完成事实，但必须明确交付尚未完成。

主代理是 STATE/HANDOFF 的唯一写入者。子代理提交结果与证据给主代理，不同时改总账。更新 STATE 前核对 revision 与 activeBatch.owner；递增 revision，先写临时文件、解析校验后原子替换。发现变化先合并事实，不最后写入覆盖。

STATE 是开发协作记录，不是分布式锁服务。两个独立 Codex 主会话不能仅凭同一 JSON 文件获得互斥；若有并行主会话，应由用户明确分支/工作目录/文件范围，必要时各自分支保存批次证据，由一个负责人合并总账。

每份证据记录至少包含：任务与验收ID、实际日期、代码HEAD及dirty摘要、命令/环境/退出码、pass/fail/skip/not-run、浏览器或live路径、复核者与模型请求/可核实运行信息、未覆盖范围、产品提交及远端状态。原始日志保留原位置，仅保存必要摘要与引用。

## 5. 分工方式

沿用当前根 AGENTS：主代理负责范围、集成和交付；默认一个实施者。两个任务只有在文件、接口、数据库、构建目录、端口和服务状态都独立时才并行，最多两个实施者。只读调查可独立并行。

明确且低风险的局部实现可按根规则选择 Luna max；需要工程判断和调用链理解使用 Sol high；复杂架构、权限、事务、恢复与数据保留使用 Astra high。常规独立复核用新的 Sol high 会话，关键边界复核用新的 Astra xhigh 会话。以当前可用工具和根规则为准，不为匹配示例改全局模型配置。

发给实施者的交接应包含：任务ID、目标、3–5验收、准确目录、文件所有权、接口、不变量、代码基线、允许检查、禁止共享资源冲突及已有证据。子代理不自行提交/推送、重启服务、扩批或再创建子代理。模型/档位未获运行时回显时写“已请求，未回显”，不靠自报身份认定配置。

## 6. 常见接续判断

| 情形 | 处理 |
|---|---|
| 只剩几分钟或上下文不足 | 完成可验证的小步并写交接，不抢做高影响迁移 |
| 命令观察超时 | 查询原 PID/call_id/operation；未有终态不重启同一任务 |
| 当前代码已有计划中的能力 | 验证与验收的差距；复用能力并缩小新增范围，保留证据 |
| 新批次与旧dirty修改冲突 | 保留旧改动、查看归属和差异；只处理本批可判断部分 |
| 真实浏览器不可用 | 完成后端与离线检查，B项记未运行；不能把该批标done |
| 无法满足关键权限/数据复核 | 关键验收阻塞；推进无依赖批次，不降级冒充通过 |
| 某功能带出大型平台需求 | 记录为本期外需求，不擅自增加新调度器/权限体系 |
| 用户再次说“继续” | 读取最新状态和当前代码，沿既有授权接续，不从GR00全部重来 |

## 7. 结束本方案

GR00–GR10 全部 done，R01/R02 为 done 或有证据的 not_applicable，关键浏览器/live验证无缺口，当前版本已完成必要回归、干净构建及独立复核，且交付同步状态明确后，形成最终能力清单。

交付时说明：能完成哪些研究旅程、已有成果如何迁移/继续、权限和方法检查覆盖到哪里、还有哪些明确限制。功能做完不代表所有学科方法都已自动验证，也不代表 Codex 会在会话结束后自行无限运行。
