# 四档权限与界面设计

> 实施更新：四档已接通实际执行，见 [权限接入验收](../../acceptance/flow-permission-modes/RESULT.md)。本机可信模式的实际边界见 [HOST-IMPLEMENTATION.zh-CN.md](./HOST-IMPLEMENTATION.zh-CN.md)。本文件其余内容保留为原设计记录。

日期：2026-10-05。代码基线：`86dcf3c90e135391c28f1301c29a09f09006cfbf`。

本批交付设计与离线交互原型，不改正式前端、运行服务或实际权限。原型所有数据是示例，选择不调用后端。本项目采用用户指定的四个名称：**只读、变更前确认、自动编辑、完全访问**。新项目默认“变更前确认”。既定侧栏、聊天区域、右侧检查区以及来源、附件、多智能体、模型和发送位置保持不变。

## 本批验收条件

1. 四档对应实际副作用和执行范围，明确默认、继承及不可实现时的状态，不用工具名称或 UI 开关代替执法。
2. 用户是唯一升权与审批者；会话、角色、子任务、固定来源和历史边界清楚，审批内容与执行内容一致。
3. 降权、撤销、排队、执行中、重开及旧数据迁移有确定规则；每次副作用和已完成请求重放重新鉴权。
4. 浅色权限菜单、设置说明和审批卡可审阅，保留布局，诚实说明文件、命令、网络和确认范围；未支持的完全访问不能假装生效。

## 权限语义

| 操作 | 只读 | 变更前确认（默认） | 自动编辑 | 完全访问（后续执行边界完成后） |
|---|---|---|---|---|
| 已授权项目资料、分配来源与历史 | 自动读取 | 自动读取 | 自动读取 | 应用内仍校验来源；另可读取执行系统用户能访问的宿主文件 |
| 项目可编辑 draft 与自己的私有准备区 | 禁止变更 | 固定变更单逐次确认 | 授权目录内自动编辑，写入时校验版本 | 宿主执行系统用户可访问的文件自动变更 |
| 新命令、脚本、测试与执行请求 | 不执行 | 确认准确执行请求，仍受执行环境限制 | 命令仍需确认；已批准的固定受限授权内可继续 | 可执行该系统用户权限内的宿主命令，不逐次询问，不提升为管理员 |
| 正式实验与规范成果整合 | 不产生新执行副作用 | 固定运行清单确认 | 沿用有效 RunGrant 与专门流程 | 应用规范流程仍检查原有授权、来源和完整性 |
| Agent 外部内容访问 | 默认关闭，只读已保存内容 | 固定请求确认或已有明确受限来源授权 | 已启用且已授权的连接器/来源；新范围确认 | 普通网络开放，可能产生第三方账户副作用 |
| 权限设置、批准、凭据配置、正式采纳 | 用户操作 | 用户操作 | 用户操作 | 受保护的应用控制面仍由用户操作 |

“自动编辑”不等于自动批准所有命令。“完全访问”也不等于获得所有 Agent 角色和正式采纳权限。模式是动作策略，执行能力、项目上限、角色、任务输入和有效授权还要共同限制实际可做的事。

只读仍允许用户发送消息，服务端记录会话、审计、用量、回执和受控进度。`task_result_submit` 单独分类为当前 attempt 的有限 `task.report`：可保存意见并结束自己的 attempt，不能创建任意产物、采纳结论或令后继任务直接越权。模式限制 Agent 操作，不封锁用户手动编辑。模型请求本身的网络与计费属于用户发起会话授予的基础服务，不是 Agent 任意联网权限。

第一版只读不提供在线预览；已有内容可检索。在线获取、系统缓存、正式导入分别分类，不能把 `paper_read`、`text_evidence_search` 等名称当成纯读证明。四档不自动启用连接器、不扩充额度、不覆盖 WorkingGrant、RunGrant、DiscoveryGrant 的来源/次数/期限。

## 界面与用户流程

### 聊天入口

将现有 `.composer-caption` 左侧的静态说明替换为 **盾牌图标 · 变更前确认 ∨**。使用现有 24px 高度，不新增工具栏行；来源、附件、多智能体、模型与发送均不移动。右侧发送快捷键提示保留。窄屏只压缩旁边说明，不将模型或发送挤出容器。

菜单向上展开，约 320px，移动端最大为视口宽度减 32px；四项各有图标、名称、一句解释和当前选择勾。底部显示“仅当前会话 · 项目授权范围”，提供“权限设置”入口。普通模式使用中性灰，完全访问启用后持续显示克制的琥珀色提示；状态不能仅靠颜色表达。

选择只读/确认/自动编辑后调用会话策略接口，提交 `expectedVersion`，等服务器返回有效状态才更新已选项。失败保留原模式并显示原因。菜单支持键盘单选、Escape、返回触发按钮焦点和点击外部关闭；运行中降权仍可用，升权只影响重新准备的新动作，不释放旧批准。

完全访问不是一点击即生效：若后端缺执行或可信身份能力，显示“暂未就绪”，可查看说明但启用按钮禁用。能力完成后，独立确认对话框列出“宿主文件、命令、普通网络、仅当前会话、不继承给子任务”，用户勾选理解范围再启用。不要提供“永久完全访问”项目默认值或以超时默认为同意。关闭对话框保留原模式。

### 设置页

在现有设置页内加入“权限”区块，不更改外层布局。展示当前会话策略、有效模式、设置来源、权限上限、文件范围、命令规则和网络范围；如选定值与有效能力不一致，二者都显示并解释原因。

“新会话默认权限”只能选前三档，默认变更前确认；保存仅影响之后创建的会话，已有会话不自动改变。项目最高允许策略是另一项安全限制，不能与默认值混淆。子任务或自动任务显示继承来源和角色限制，不允许在其页面自行升权。

详细记录使用现有审计入口：谁在何时从哪档改到哪档、策略版本、实际范围、授权或撤销理由；保留已执行事实。列表状态用“等待确认”“权限已收紧”“正在停止”“退出状态未确认”，不用一个绿色勾代替生命周期。

### 聊天审批卡

待确认操作插入当前聊天，并在侧栏显示等待状态。文件操作显示路径、变更差异、目标版本；命令显示准确 argv、cwd、执行环境与网络；均来自同一服务端固定 action。按钮为“允许本次”“拒绝”，另有“查看变更”。第一版不做泛化“永久允许同类命令”：连续操作复用既有明确范围的 grant。

批准或拒绝前当前动作暂停；重新打开仍保留待决卡。权限批准永不倒计时自动通过。内容或策略版本改变则旧卡标记失效，重新准备动作；一次批准不能在只读下跳过模式约束，用户需先明确切换允许变更的档位。

离线原型：`../ui-redesign-2026-10-03/permission-modes.html`。它演示前三档选择、会话/默认值区别、只读拒绝效果与审批卡；完全访问保持未就绪。原型不保存浏览器存储，不发送网络请求，不改真实研究数据。壳体是静态示意，交互验收不冒充正式前端尺寸回归。

## 后端改法与现状证据

本项目目前仅暴露受控自定义工具，`packages/pi-adapter/options.ts` 的 `noTools: 'builtin'` 保持不变。不能通过直接开启 Pi builtin bash/edit/write 绕过现有项目接口。

`packages/policy/permissions.ts` 的 `READ` 包含 `task_progress_report`、`task_result_submit`，不是安全上的纯只读集合。Operation 的幂等分类也不能当作权限分类。新增一个统一 effect 判定，复用 Registry、ApprovalService、角色与现有 grant 服务，不建立另一套平行审批。

建议策略对象保存：

```ts
type PermissionMode = 'readOnly' | 'confirm' | 'autoEdit' | 'fullAccess';
// 概念字段；实现时沿用项目既有 Row.version / Actor / grant 引用。
interface PermissionPolicy {
  mode: PermissionMode;
  schemaVersion: number;
  epoch: number;
  source: 'project-default' | 'explicit-session' | 'migrated';
  readableRoots: string[];
  writableRoots: string[];
  networkPolicy: object;
  executionProfile: string;
}
```

项目 defaults/max-policy 与会话 policy 分开持久化。服务端计算有效权限为：

`执行能力 ∩ 项目上限 ∩ 会话策略 ∩ 父任务授权 ∩ 角色 ∩ 固定输入 ∩ 有效 grant/来源`。

这不是四个数字取最小值：网络、文件范围、命令和角色必须分别求交。模型提示词和工具展示依据结果生成，但不参与最终执法。Actor 来自可信 transport/调度器，不能接受模型或任意请求体声明的 `type=user`。

Registry OperationSpec 增加服务端 `effects(context, input)`，产生不可变 ActionManifest：operation、project/session/task/attempt、policyEpoch、来源引用、目标版本、文件 before/after digest、执行 argv/cwd/镜像或可执行文件摘要/环境摘要/挂载/网络/资源、有效期限和总 digest。批准显示内容与落地执行都使用这个 manifest。来源、参数、目标版本或 epoch 改变均不能复用旧批准。

审批的精确文件列表只能保证直接受控文件操作，不能证明任意 shell 只会修改列出的路径。命令必须受真实文件/网络执行边界限制，否则确认界面需要展示它完整可达范围。路径处理必须解析真实目标并防 `..`、大小写别名、junction/symlink、硬链接与替换重绑定；先验证后执行时防止 TOCTOU。draft 写入要求 `expectedDigest`/CAS，冲突重新读取生成新变更，不覆盖并发写入。

统一授权顺序：准备/排队 → 出队准入 → 每个落盘、外部请求、进程启动之前 → 异步结果提交之前 → completed replay 返回内容之前。准入与撤权事务有明确先后，副作用用持久 intent/回执记录；不能承诺已发出外部请求可被撤回。不可读内容不能从缓存回执泄漏；旧写请求命中幂等缓存也不能越过新策略，历史查看使用独立只读入口。

现状 `workspace_write` 不允许 Agent 修改共享项目区。开放项目 draft 是新增能力，仅交互主协调者通过受控入口进行；子任务限定自己的准备区，产物合并由协调者另行判定。不改冻结 snapshot、Run 输入、正在审查的候选、已接受历史、其他会话私有区或控制面。

### 完全访问的真实前置条件

现有 `apps/server/http.ts` 主要验证回环 Host/Origin，`operation-routes.ts` 使用静态 `USER`。同一系统用户下的任意 shell 可以自行访问 owner HTTP、DB、密钥或认证材料。另起一个 Node 进程、清理环境变量或加入可被同 UID 读取的 token 都不足以保证“只有用户可升权”。

要兑现真实宿主权限，又保护应用审批和权限记录，须同时满足：

- HTTP、CLI、旧路由和 IPC 全部使用可信 principal；Agent 无 owner 凭据，也不能伪装 owner。
- 执行 broker 与控制面之间存在真实 OS 安全主体/更强隔离。目标执行系统用户无法读写控制面 DB、程序、配置、审批密钥及 owner 身份，无法提权操纵控制面。
- Owner 确认通道不受这个宿主执行身份支配；同 UID 浏览器 cookie/本地 token 仍可窃取，不能作为最后边界。需要受保护用户确认或独立受信设备上的用户会话等可验证方案。
- 核验实际 Windows 身份、ACL、网络与进程恢复/撤销行为；单独 fork 和 cwd 不算 OS 沙箱。没有通过核验时 `fullAccess.available=false`，也不开放任意宿主命令。

完全访问只给用户显式选择的交互主协调会话，子任务/自动唤醒不继承，最高 autoEdit 并取自身角色与来源交集。其宿主普通文件访问不能再声称受 Task 固定输入范围限制。控制面保护与宿主访问是两种不同边界。

宿主 full 能使用该执行系统用户可读取的第三方凭据并产生外部副作用。因此不能宣称“完全访问下对外发布绝对禁止”。受保护的应用正式采纳/批准流程仍要求用户；系统账户已拥有的外部权限不会被这个应用域规则神奇隔离。

## 继承、降权、恢复与迁移

- 新项目默认 confirm；新会话固定默认策略版本。用户会话覆盖值持久保存，重开按当前项目上限及有效授权重新计算。项目默认值改变不自动改变旧会话。
- reviewer 最高只读；其他角色保留既有 ROLE_TOOLS 及固定来源要求。子任务最高 autoEdit，无宿主 full；父任务降权/授权失效使后继任务重新判定，升权不自动放宽旧任务。
- 策略修改带 expectedVersion；事务中提高 epoch，关闭越界准入，使旧 pending action 失效。降项目上限收紧所有相关会话；放宽只提供可选择能力，不自动升级旧会话或任务。
- queued 工作出队重新检查，越界标 `blocked_by_policy`，不按旧快照继续启动。升权后也必须重新准备动作，而不是释放旧批准或恢复未知请求。
- 运行中先阻止新授权，取消已跟踪受限作业。显示 `revocation_pending`；确认受管进程结束才显示完成。退出或外部效果不明显示 `unknown` 并阻止自动恢复/发布。已授权并开始的 effect 如实标“撤权前已开始，正在停止”。
- Full 的撤权只能阻止新 broker 调用并停止能跟踪的作业，不能保证清除脱管进程、撤回网络或还原文件。存在残留/未知效果时，区分“新请求按只读限制”与“旧完全访问效果待核实”，不能声称宿主已恢复完整只读隔离。
- 重启恢复持久 epoch、grant 用量与 action 回执；旧 generation/lease 失效。未知外部请求不能自动重试；到期不再准入，撤销按既有授权血缘使后续来源引用失效。
- 已发生的运行、批准和变更事实保留。模式降权不改写历史批准，来源可读性及有效性仍按当前权限检查。
- 旧会话迁移 `legacy-restricted`，UI 显示“变更前确认 · 旧会话待确认”。下一次新 Agent 执行先由用户选择模式，缺字段不自动升权。旧 grant 与历史均保留，使用时与新策略求交。
- 升级前进入可恢复维护准入屏障：不再派发新 Agent 工作，持久记录队列/回执，排空或取消已跟踪旧 worker 并确认退出。运行中的正式外部作业保留固定 grant 和追踪记录；效果未确认先挂起恢复，不盲目重启。不能只迁移 DB 就让旧 worker 在没有 epoch 的情况下继续执行。

## 实施顺序与落点

按顺序分批，每批一条可验收流程，不并行修改共享数据库/运行资源。

1. **公共授权闭环**：`packages/domain/types.ts`、`packages/policy/permission-policy.ts`、`permissions.ts`、Registry 与 approvals；可信 transport 身份先覆盖所有 owner/agent 入口，effect 分类无漏项，未知 effect 默认拒绝；保持 builtin 关闭。
2. **三档与界面**：旧数据准入迁移、项目默认/会话接口、composer-caption 菜单、设置与聊天审批卡；只开放现有受控服务能兑现的能力。自动编辑项目 draft 是单独有 CAS 验证的受控扩展。接口返回 selected/effective/available/reasons/epoch/version，UI 不自行猜测权限。
3. **完全访问**：独立可信 owner 通道与隔离 broker 验证后，才提供宿主文件/命令/网络工具；初期只交互主协调会话、单次会话授权，重启 full 会话需要用户再次启用。若重开仅页面导航且授权未过期，显示已有授权；会话/执行端重启、过期或未知状态不静默恢复 full。

建议 UI 文件：`apps/web/src/workbench.tsx`（现有 composer-caption）、`composer-controls.tsx`、`data-views.tsx`、`models.ts`，样式在既有 light-workbench 相关资源内定域；不引入新的前端框架。现有项目无 Tailwind/components.json，保留已有组件，使用 shadcn 的 Popover/RadioGroup/AlertDialog 组合思路而非为了四项菜单迁移全站。

关键回归反例：只读的 READ 混合写入；旧 grant 越过新策略；reviewer 未分配来源；批准后更换源码/argv/cwd/epoch/真实路径；Agent 自构 USER 或调用旧 owner 路由；撤销与出队/异步提交交错；completed replay 泄漏；重启复活授权或重置额度；历史事实丢失；full 未退出却显示已安全只读。
