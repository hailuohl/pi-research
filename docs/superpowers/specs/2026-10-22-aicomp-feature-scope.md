# AIC「AI+开源」参赛功能取舍：5日MVP

版本：1.0；2026-10-22。本文是长期通用科研设计的参赛范围覆盖层：只决定本轮功能取舍，不宣称实现完成。五日目标不是“把长期产品计划按比例压缩”，而是选择一个能展示实质技术贡献的窄而完整的功能。

官方赛题强调真实问题、AI与开源生态的实质融合、原创或合法授权基础上的实质改进、可运行/演示/验证的成果；仅调用通用模型、简单部署或界面包装不足。评分重点包括实现完成度与可验证效果、创新、AI与开源融合和开放复用。正式实施前再次核对官方页面、附件和截止时间。

## 1. 参赛产品主张

建议主张：

**研舟π：面向AI辅助科研/开发的可验证任务胶囊（Verifiable Task Capsule）**。

它不是再做一个聊天机器人或通用Agent，而是把一次AI工作变成一个可检查、可继续的工程对象：任务目标、明确范围、执行记录、验证证据、状态不确定性和下一步都绑定到同一个任务快照。中断后可以接续；结果不能只凭模型自述宣布完成。

参赛方向建议选择“AI开发工具与开源协作”，可补充“开源项目改进与生态贡献”。最终由参赛团队确认。

这个名称只是设计命名。实现时应复用当前任务/Run/Attempt/操作/证据/交接结构；如果代码里已有等价能力，则把它作为基线能力，实际新增应集中在缺失的绑定、验证或恢复环节，不能重新造一个平行系统。

## 2. 本轮必须修改/新增的功能

### F1. 任务胶囊（P0）

将一次目标明确的AI工作收敛为单个可浏览的工作项。最小字段：
- 目标与成功条件；
- 允许的项目/文件/操作范围；
- 本次计划与用户确认状态；
- 当前执行状态及原Task/Attempt/Run/operation引用；
- 验证清单与实际结果；
- 输出产物、代码diff或回执引用；
- 未完成事项、阻塞原因、准确下一步；
- 基线/结果快照摘要与创建时间。

约束：
- 不复制第二份执行状态机；执行状态以原系统为真相源。
- 用户能看到“计划、执行、验证、交付”四段，点入可查原记录。
- 计划修改后旧批准失效或需要重新确认；不能沿用旧批准执行新范围。
- 一次任务可以没有Run；例如文献整理/代码审查，不能强制填实验字段。
- 不增加复杂项目仪表盘。首期在现有会话/任务视图内增加一张摘要卡/详情面板即可。

### F2. 证据化验证门（P0，作品核心差异）

AI不能自己声称“完成”。任务状态进入 completed/delivered 前，必须有适用的真实验证证据：
- 具体执行了什么命令/操作；
- 对应的代码/输入快照；
- 退出码和真实测试统计；
- pass/fail/skip/not_run及原因；
- 未覆盖范围；
- 输出产物或差异的引用。

最小规则：
- 测试通过只证明所运行的检查通过，不推导科学结论正确。
- skip/not_run不等于pass；关键验证未运行时状态应是“验证未完成”。
- 测试结果必须关联当前被验证的快照。源码变化后，相关旧证据标为stale，不可静默当成最新结果。
- 只在任务类型确实需要时运行测试；文献/理论任务可以用引用完整性、人工检查清单或明确的论证检查作为适用验证，不虚构命令。
- 模型生成的验证摘要只是展示层，底层证据来自真实工具结果。

如果当前已有验证/Review机制，优先添加“证据与当前任务绑定”的缺口，不另造测试运行平台。

### F3. 可靠接续与未知状态处理（P0）

用户关闭会话后能恢复原任务：
- 恢复原Task/Attempt/operation ID、已完成/未完成检查；
- 展示最后一条真实回执及其时间；
- 将“底层结果未知”与“明确失败”区分；
- 对unknown先inspect/reconcile原操作，不盲目启动新操作；
- 已完成步骤不重复执行；未完成步骤只从明确安全的检查点继续；
- 恢复后的状态由实际记录重建，不能只依赖模型的聊天摘要。

不要做通用项目记忆平台。只需要一个明确的“继续上次任务”入口和可审计的任务交接。

### F4. 基线与差异证明（P0）

参赛演示需要清楚证明本次改进：
- 在同一合成/公开样例上，展示改进前后流程；
- 用Git diff、测试和运行记录证明本次实际修改；
- 记录失败场景与边界；
- 只报告真实测量数据，不承诺未经测量的效率提升百分比。

如果没有可靠的量化基线，使用可重复的行为对照：旧流程无法准确恢复/关联验证，新流程能回到同一任务并显示真实证据。不要伪造“提升80%”等数字。

### F5. 参赛演示/开源合规包（P0）

这不是产品里的大功能，而是本轮交付功能的一部分：
- 一条3–5分钟可重复演示路径；
- 最小运行说明、环境和实际命令；
- 架构图与关键数据流；
- 实际使用的代码、依赖、模型、数据、素材及许可证/授权清单；
- 本次自主改动与上游已有能力对照；
- 真实测试日志/摘要和版本号；
- 不公开无权再分发内容，不在材料中出现学校名称、学校Logo、指导教师信息；
- 报告、视频、仓库提交必须对应同一代码版本。

## 3. 本轮明确不做/删除出五日范围

以下功能仍可作为赛后路线，但从五日MVP移除：
- 完整“项目概览”仪表盘及全部对象目录；
- 全量通用项目上下文/决定系统；
- 五种研究类型及方法覆盖目录的完整体系；
- 通用手工比较表、矩阵编辑器、冻结与导出系统；
- 多Agent批量提取与细粒度分片权限体系；
- 通用Evidence关系图和科学可信度分析界面；
- 多格式成果编辑器、完整第三方格式同步；
- 全量数据库迁移、项目生命周期扩展、云部署、用户/团队权限体系；
- 大规模UI重设计、全仓重构、性能优化（除非直接阻断演示）。

不是永久删除，而是避免在比赛前引入大规模新数据模型和权限边界。

## 4. 对现有功能的修改原则

| 现有能力 | 参赛版调整 |
|---|---|
| ResearchBrief/计划 | 只展示目标、范围、验收与确认状态；不扩展成复杂工作类型系统 |
| Task/Attempt/Run | 保留为真实执行来源，任务胶囊仅引用它们 |
| operation registry/权限 | 所有动作继续走原注册与授权；计划确认不能绕过权限 |
| 研究交接/持续执行 | 复用恢复机制，补齐当前任务摘要和真实证据关联 |
| 报告/产物/工作区 | 只保存最小交接、验证摘要和演示所需产物；不做全新编辑器 |
| 前端入口 | 只增加任务摘要/验证证据/继续任务的必要入口，避免全局布局改造 |
| 日志/测试 | 关联当前任务和代码快照，记录真实结果；不新增另一个测试平台 |
| 多智能体 | 保留为可选能力；参赛演示优先选择稳定、可重复的单任务闭环，除非多Agent是本次核心差异的必要组成 |

## 5. 五日验收门槛

Day 1：
- [ ] 选定一个真实可复现的任务问题。
- [ ] 写明原版本表现、本次改变、可证明差异。
- [ ] 找出已有实现，明确仅新增缺口。
- [ ] 确定可公开代码/依赖/模型/数据范围。

Day 2：
- [ ] 从真实用户输入生成并确认任务胶囊。
- [ ] 真实执行一个操作，输出与原任务绑定。
- [ ] 至少一条端到端路径可复现。
- [ ] 测试/验证结果来自实际执行。

Day 3：
- [ ] 重开会话后能恢复原任务与证据。
- [ ] 一个unknown/失败/拒绝场景显示准确。
- [ ] 重试不会重复副作用。
- [ ] 相关测试、构建和独立复核完成。

Day 4：
- [ ] 完成作品简介、技术报告、资源/许可证清单、架构图、视频脚本。
- [ ] 报告和脚本只描述已实现能力。
- [ ] 所有量化结果有原始证据。

Day 5：
- [ ] 冻结范围，真实环境重跑。
- [ ] 3–5分钟演示视频和技术报告PDF可播放/打开且符合官方大小要求。
- [ ] 仓库提交、报告、视频和资源清单版本一致。
- [ ] 匿名、权属、许可证、秘密和第三方资源复核通过。
- [ ] 平台提交成功以真实回执为准。

## 6. 建议的比赛故事线

用同一个可公开的样例展示：

1. 给研舟π一个具体开发/研究任务；
2. 系统把任务范围、验收和允许操作显示清楚；
3. 用户确认后，系统执行一项真实操作；
4. 系统运行实际检查并显示证据，而不是模型说“已完成”；
5. 人为制造失败或中断，重开后恢复原任务并正确处理unknown；
6. 打开差异、测试结果、运行说明和开源资源清单。

这一条流程同时展示AI作用、工程可靠性、开源改进和可复现性。不要同时演示十个零散模块。

## 7. 决策原则

当某项实现预计超过半天且不是端到端闭环的必要条件，默认移出五日范围。任何新功能必须能回答：
- 参赛者真实遇到的具体问题是什么？
- 相比当前仓库新增了什么？
- 用什么可重复证据证明改善？
- 是否引入新的权限、迁移或不可逆风险？
- 若不做，核心演示是否仍成立？

如果核心闭环在Day 2末仍不稳定，继续减功能，优先交付可靠性与证据链，而不是增加UI和Agent角色。
