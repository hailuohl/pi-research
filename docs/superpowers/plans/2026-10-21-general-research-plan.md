# 研舟π：五日产品功能改进计划

版本：产品冲刺 v3.0；日期：2026-10-22。目标是五个工作日内完成一组真实的产品功能改进，不包含竞赛报名、技术报告、演示视频、资源披露或提交材料任务。长期设计见 [通用科研工作台详细设计](../specs/2026-10-21-general-research-design.md)。

## 目标

让研舟π中的一项AI研究/开发工作更容易理解、核查和继续：用户能看清目标与范围、知道实际执行到了哪一步、核验真实结果，并在中断后恢复原任务。实现必须复用现有 ResearchBrief、Task/Attempt/Run、OperationRegistry、权限、交接、证据和工作区能力；不得另建执行内核、调度器、权限体系或平行状态库。

**原则：先审计已有能力，只实现当前缺失的部分。** 不因为方案里提出了“任务胶囊”就重复实现已有Task、Campaign或交接机制。

## 五日范围

| 日 | 主要功能改进 | 可验收结果 |
|---|---|---|
| Day 1 / P0 | 当前能力审计与差距确认 | 明确现有对象、用户痛点、最小修改范围和回归基线；若功能已存在，只补缺口 |
| Day 2 / P0 | 任务摘要与状态可解释性 | 在现有任务/会话视图显示目标、范围、真实状态、产物、阻塞与下一步，链接回原始对象 |
| Day 3 / P0 | 证据化验证结果 | 任务关联真实验证命令/操作、代码或输入快照、退出码/结果及验证范围；区分pass/fail/skip/not_run，过期证据标stale |
| Day 4 / P0 | 中断恢复与unknown安全处理 | 继续原Task/Attempt/operation；unknown先核对原操作，不盲目重跑；修复经当前证据确认仍存在且阻断该流程的恢复缺陷 |
| Day 5 / P0 | 集成、交互打磨和交付 | 完成一条真实端到端流程、失败/拒绝反例、跨会话重开；必要回归与独立复核通过，更新说明与状态 |

若某日任务提前完成，不自动扩展到大型新模块；优先补足关键反例、可访问性、错误提示和恢复测试。

## 产品功能要求

### P1. 任务摘要（最小“任务胶囊”）

放在现有任务或会话详情中，不新建复杂项目仪表盘。显示：
- 目标/成功条件和已确认的操作范围；
- 原Task/Attempt/Run/operation引用及真实状态；
- 已完成、未完成、阻塞和下一步；
- 当前代码/输入快照引用；
- 验证结果与输出产物链接。

执行状态以原对象为准，摘要只是投影。任务可不含Run，例如文献整理、研究讨论和代码审查，不强制实验字段。计划或范围变化时，按原授权规则重新确认，不能复用旧批准执行新范围。

### P2. 验证证据与当前快照绑定

- 记录实际命令/操作、快照摘要、开始/结束时间、退出码和可获得的真实测试统计。
- 结果状态为pass/fail/skip/not_run；未运行不等于通过。
- 每项验证标明覆盖范围；测试通过不推导科学结论正确。
- 源码或输入快照变化后，相关验证证据标为stale，不能冒充当前结果。
- 由宿主执行记录和实际结果产生证据，模型只负责解释展示，不能自报pass。
- 复用现有验证、审查和产物服务；不开发新的测试执行平台。

### P3. 安全接续与unknown

- 从真实存储恢复原任务标识、最后回执、已完成检查、未完成项和下一步。
- 断连/观察超时/取消请求不直接等于任务失败或进程已停止。
- unknown先inspect/reconcile原ID；没有明确安全检查点时不自动重启可能有副作用的操作。
- 已提交结果不重复执行；未完成步骤按现有Task/Attempt状态机和幂等契约继续。
- 不依赖模型聊天摘要作为唯一恢复来源。
- R01（启动准备失败后launching标记残留）和R02（Worker观察超时与宿主命令时限冲突）先核实当前代码。仅当仍存在且影响本次流程时纳入修复；否则以当前证据记录不适用，不为完成计划而机械改代码。

## 本轮明确不做

以下仍属于长期产品路线，但不进入五日必做范围：
- 完整项目概览仪表盘、覆盖所有对象的全量目录；
- 全量通用上下文/决定体系；
- 完整学科方法目录；
- 通用比较表、证据矩阵和冻结导出系统；
- 批量多Agent文献提取及专用细粒度权限体系；
- 大型成果编辑器、第三方格式深度同步；
- 云部署、账号/团队权限平台、全局数据库迁移或全仓重构；
- 竞赛简介、技术报告、视频、报名、提交包等竞赛文稿任务。

除非某一项是本次端到端流程的必要依赖，否则移到赛后产品迭代。

## 验收门槛

### Day 1：基线与差距
- [ ] 核实当前HEAD、分支、dirty改动、运行中进程和测试入口。
- [ ] 对照现有ResearchBrief、Task/Attempt、交接、验证和权限能力，列出“已有/缺失/本轮修改”。
- [ ] 选定一个真实用户流程及3–5条验收条件。
- [ ] 保留既有未提交改动；不因审计重置或清理工作树。

### Day 2：任务摘要
- [ ] 用户能在现有界面看懂目标、范围、状态、阻塞和下一步。
- [ ] 状态来自真实对象，链接跳转到正确原记录。
- [ ] 旧项目和不含Run的研究任务仍能使用。
- [ ] loading、empty、error、denied、unknown等适用状态明确，不把读取失败显示为空。

### Day 3：验证证据
- [ ] 验证结果绑定当前代码/输入快照及实际执行回执。
- [ ] pass/fail/skip/not_run和覆盖范围清晰区分。
- [ ] 快照变化使相关旧证据标stale。
- [ ] 至少一个失败反例能证明模型不能仅凭文字把任务标成验证通过。

### Day 4：恢复与幂等
- [ ] 关闭会话后可恢复原任务和已保存结果。
- [ ] unknown时先核对原操作，不创建替代操作。
- [ ] 重试不会重复已完成的副作用。
- [ ] 如果R01/R02仍影响此流程，增加能够复现原错误的回归测试；如果不影响，保留当前证据并说明。

### Day 5：集成与收口
- [ ] 一条真实端到端用户流程完成：输入目标→查看计划/范围→确认→执行→查看真实验证→关闭并重开→继续。
- [ ] 一个失败/拒绝/unknown场景符合预期。
- [ ] 相关单元/集成测试、类型检查和构建通过；所有未运行项明确记录。
- [ ] 独立复核针对当前代码快照完成，无阻断问题。
- [ ] 更新用户文档、STATE.json、HANDOFF.md；只提交本批相关文件，保留其他dirty改动。

## 工程规则

- 开工前读根AGENTS.md及本计划、STATE、HANDOFF；以真实工作树为准。
- 不默认新建文件或新数据模型；先查是否已有同义实现。
- 不为简单展示复制第二份状态；投影应链接原对象并可从源重建。
- 不把全量历史放入单个state响应；按需读取、分页。
- 不扩大Agent权限，不因用户能浏览项目就授予Agent全项目读取。
- 开发阶段只跑定向检查；集成时运行适用回归和独立复核。
- 只将真实执行的检查记为pass。产品任务状态、验证状态和Git远端同步分别记录。
- 五日后若核心流程稳定，停止本轮并根据真实使用反馈重排长期路线，不自动扩建新模块。
