## 一、比赛导向与作品定位

官方赛题支持“AI开发工具与开源协作”和“开源项目改进与生态贡献”，要求作品具有可运行核心功能、可演示流程或可核验开放成果。仅部署现有项目、简单调用通用模型或界面包装不足以构成充分创新。官方评分中，实现完成度与可验证效果25分，创新性20分，AI与开源融合20分，开放成果15分，问题价值15分，材料规范5分。

建议主方向为“AI开发工具与开源协作”，结合“开源项目改进与生态贡献”。最终方向、作品名、报名状态与开放范围由参赛团队确认。

作品切口：帮助个人研究者/开源开发者把AI辅助开发任务变成可接续、可验证、可恢复的闭环，解决任务容易丢失、计划和执行难对齐、失败状态不清楚、成果难以复现的问题。创新必须通过实际新增差异与测试证据证明，不能把现有能力冒充本次新增。

## 二、五日MVP边界

只完成一条端到端流程：

1. 从真实项目状态恢复当前任务、代码版本和已完成/未完成事项。
2. 生成可执行计划，写清目标、允许范围、验收条件、验证命令与下一步；由用户确认。
3. 利用现有Pi/工具链执行一个有实质差异、风险可控的小改进。
4. 执行真实验证，记录pass/fail/skip/not_run、日志和代码快照；不把模型文字当成执行证据。
5. 跨会话恢复任务并输出可复现运行说明、资源/许可证清单、架构说明和演示流程。

优先复用现有会话、Pi、Task/Attempt、操作注册、权限、证据、工作区与交接能力。不得另建调度器、执行内核、权限体系或存储引擎。

本轮不要求实现完整比较表、证据矩阵、通用研究仪表盘、全学科方法体系、批量多Agent提取、复杂成果编辑器、云部署或全仓重构。现有能力若已满足需求，验证后复用。

## 三、五日工作安排

| 日期/日程 | 重点 | 当日交付 |
|---|---|---|
| Day 1 | 选题、基线、真实差异 | 核对比赛规则和许可；确定单一作品切口；记录当前基线；复现一个痛点；完成最小原型或定位最小实现差距 |
| Day 2 | 核心流程可运行 | 真实任务恢复→计划确认→一次受控操作→结果回执，至少一条完整演示 |
| Day 3 | 验证与恢复 | 测试/构建、失败/中断/重开、幂等反例、修复核心阻断、独立只读复核 |
| Day 4 | 展示与开放成果 | 技术报告初稿、资源披露清单、3–5分钟演示脚本、架构图、真实测试证据、运行说明 |
| Day 5 | 冻结与打包 | 从目标环境重跑、只修提交阻断、录制视频、导出PDF、核对链接/匿名/许可、形成提交清单 |

建议Day 5结束时核心作品和材料全部冻结，之后只处理阻断提交的问题。若Day 2结束仍没有可运行的端到端流程，立即缩小功能范围，不挪用全部材料制作时间继续堆功能。

## 四、逐批执行与验收

### S0 — Day 1上午：基线与参赛范围

- [ ] 读取根AGENTS.md、当前STATE、HANDOFF、设计和计划；检查HEAD、分支、dirty文件、暂存区、在途进程及远端状态。
- [ ] 确认参赛方向、报名状态、团队授权、可展示内容及可公开范围；复核官方最新通知。
- [ ] 列出“上游已有能力 / 本次实际改动 / 演示效果”三列，选定一个有证据的真实痛点。
- [ ] 建立核心路径、失败路径、重开路径的验证矩阵。
- [ ] 核对实际依赖、模型、数据、素材和代码许可证；未经核实的资源不声明可公开再分发。

验收：切口清楚、基线真实、文件归属明确、创新点可通过实际差异验证、许可风险有处理方案。

### S1 — Day 1下午至Day 2：实现核心闭环

- [ ] 用户可以给出具体目标并查看计划：目标、文件/操作范围、验收条件、验证方式、风险与回退。
- [ ] 用户确认后，只执行授权范围内的操作；复用现有权限和幂等机制。
- [ ] 结果能关联真实Task/Attempt、代码差异或操作回执，不把模型生成的文字当作真实执行。
- [ ] 真实显示pass/fail/skip/not_run及原因，不把失败或未知伪装成成功。
- [ ] 完成一条端到端真实演示，并准备一个失败/拒绝场景，证明作品边界。

验收：功能真实运行；至少一项本次新增或实质改进；可解释与原基线的区别；没有越权。

### S2 — Day 3：质量、恢复和反例

- [ ] 保存任务的可恢复状态和最小交接；结束会话后新会话能恢复同一任务。
- [ ] 覆盖一种失败、中断或超时；观察超时不自动等于底层任务失败。
- [ ] 验证重复请求/恢复不会造成重复副作用。
- [ ] 运行本批相关单元/集成测试、类型检查和构建，确保dist对应当前源码。
- [ ] 独立只读复核差异、权限、异常状态、测试证据与文档一致性。
- [ ] 修复阻断演示的缺陷；非关键增强延期。

验收：恢复真实可用；关键路径验证有证据；反例通过；未运行的路径明确披露。

### S3 — Day 4：参赛材料与开放成果

- [ ] 作品名称不超过20字，作品简介不超过300字。
- [ ] 技术报告按官方大纲写作：问题与场景、方案、AI与开源资源、自主开发、实现过程、效果验证、创新与开放价值、风险合规。
- [ ] 资源清单覆盖名称/类型、版本/来源、许可证或授权类型、使用方式、关键义务、自主开发边界、合规状态和开放方式。
- [ ] 准备3–5分钟演示脚本：真实问题→输入→操作→核心结果→失败/边界→可复用成果。
- [ ] 准备架构图、关键截图/终端记录、真实测试摘要、代码diff和版本号。
- [ ] 检查成果链接在评审期内可访问，且不包含密钥、个人信息、私有研究数据或无权再分发的第三方内容。
- [ ] 在技术报告中如实说明生成式AI/Agent参与环节、团队审核修改与验证。
- [ ] 参赛材料不得出现参赛学校名称、学校Logo或指导教师信息。

验收：报告和视频由真实功能支撑；效果数据可核验；第三方资源披露完整；开放范围符合权利与许可证要求。

### S4 — Day 5：冻结与打包

- [ ] 冻结功能范围，只修提交阻断与P0缺陷。
- [ ] 在目标环境从头执行安装、启动和演示流程，记录准确命令、版本和限制。
- [ ] 从已核实代码快照运行关键测试/构建，保存实际退出码与测试统计。
- [ ] 录制3–5分钟MP4，文件不超过300MB，画面清楚且无敏感信息。
- [ ] 技术报告导出PDF，建议正文15页以内、文件不超过10MB。
- [ ] 核对作品名称、简介、方向、成果链接、资源清单和佐证材料。
- [ ] 确认报告、视频、仓库代码指向同一版本；未实现能力不得写成已实现。
- [ ] 最终独立复核并备份材料；平台提交成功必须由真实回执确认。

验收：说明可以复现运行；核心演示成功；材料齐全、真实、匿名和许可合规。打包完成不等于平台已提交。

## 五、实现原则

- 先检索已有实现，同义能力存在时只补差距。
- 以当前实际工作树为准；不要用纯HEAD副本覆盖或漏掉未提交能力。
- 每批只改核心流程必要文件，尽量避免公共schema、数据库迁移和全局UI改造。
- 新记录只有在必要时才引入，并同步考虑备份、恢复、生命周期和回滚。
- 不为参赛将私密仓库擅自设为公开；按规则和许可决定受限提交或开放成果范围。
- 任何测试结果、用户反馈、性能数字、演示状态必须来自真实执行，不得编造。
- 作品材料必须如实区分原项目已有能力、本次自主改进和AI辅助开发部分。

## 六、赛后保留的长期计划

下列功能仍在长期设计范围内，但不属于五日参赛MVP：完整项目概览/目录扩展、通用上下文与决定系统、完整研究类型方法覆盖、全功能比较表、固定范围多Agent提取、证据矩阵、复杂成果编辑导出、全学科综合旅程与大规模生命周期迁移。

赛后回到原详细设计，根据真实参赛反馈和剩余需求重新排期，不在本轮临时扩建。

## 七、状态和交接

- 将STATE.json切换为竞赛冲刺计划版本，记录当前Day、owner、验收、阻塞与下一步。
- 每日结束更新HANDOFF.md，写真实完成、测试、失败、未运行、阻塞和准确下一动作。
- 任务状态和验证证据分开；只有实际运行的检查才可记pass。
- 每次提交只包含本批明确改动；保留原有dirty文件，核对远端提交。
- Day 4结束后不再新增功能，除非它是提交阻断。
