# 会话归档与删除

用户已授权补齐会话列表归档、删除入口及验证。本批只交付这一条清理流程，不改整体布局，不处理文稿卡片，不清理用户真实数据。

## 设计与接口

- 复用现有归档接口，并增加 `POST /sessions/:id/unarchive` 和 `POST /sessions/:id/delete`。三者接受 `expectedVersion`，删除另需 `confirmTitle` 与冻结标题一致。归档、删除先在同一事务核验版本、身份、项目和忙碌状态，再停止后续调度，最后更新会话。
- 删除采用 `Session.deletedAt?: string` 与 `state='archived'` 的逻辑删除。所有会话目录排除已删除项，直接会话入口返回 `SESSION_DELETED` / 410。保留消息、原生历史、工作区、子分支和全部科研记录，不做级联物理删除。删除不提供恢复按钮；取消归档仅允许未删除会话，回到 idle，不恢复旧执行权或排队内容。
- 列表行提供管理操作，沿用现有 Modal；确认框冻结项目、会话、版本、标题、请求幂等键。请求中切项目/会话、迟到响应和失败均不能误改新上下文。删除当前会话后选其他有效会话或显示空态，刷新和重开不再选回删除项。
- 优先复用现有 archived 和 onStop 约束，只补实际可达的调度、权限或异步操作缺口，不做模块重构或新增依赖。

## 统一验收条件

1. 活跃会话可归档，在归档分类找到并取消归档；消息与历史保留。
2. 确认删除后活跃、归档、全部目录及重开都不再显示；关联分支、文件与研究记录保留。
3. 运行中、任务会话、未完成执行或有效租约阻止清理；归档项目、越权、旧版本和错误标题均无副作用。
4. 删除当前/非当前会话、切上下文、同拍双击、请求失败或迟到回执均只作用于冻结目标；旧队列、权限和自动化不会因取消归档复活。
5. 新测试先暴露缺口再通过；主代理完成影响集、全量回归、干净构建、隔离浏览器关键路径和独立 Astra/xhigh 复核，之后仅提交并推送本批差异。

## 范围与风险

预计触及 Session 类型、会话服务/目录、HTTP、列表/App 接线、极少量行操作样式、对应测试；调度/权限仅在当前调用链存在实际清理后复活路径时补守卫。后台繁忙应拒绝而不是静默取消仍在执行的研究。用户真实验证库只作只读证据，不执行清理。模型与档位分别记录请求值，工具不回显实际值时写“已请求，运行时未回显”。
