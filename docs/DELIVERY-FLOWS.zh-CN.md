## 首条闭环：指定源码到结果回查

默认验收任务沿用原计划的回归实验：从指定 degree=2 子实验源码继续实现一个非白名单 Python 研究程序，保留项目初始 degree=1 副本。它是科研流程验收任务，不凭一次运行宣称科学发现。

固定放行条件：

1. 用户在工作台选定子实验与固定 revision；Agent 实际读取该版本并在独立私有工作区实现，旧来源不变。
2. 当前源码与命令、固定镜像、资源、数据一起请求开发测试批准；真实容器完成测试，失败日志可回查，结果绑定精确候选源码。
3. 独立审查明确通过、拒绝或待补证；没有审查通过和用户整合批准，不创建已采纳子节点。
4. 审批后的源码、Git commit、CAS 快照、测试及审查互相定位。Git 不推送远端；既有源码历史、审批和 Run 摘要不被重写。
5. 正式 Run 再单独批准，在固定 Docker 镜像中执行新 Python 程序并产生真实指标和文件。缺必需输出不报完整；开发测试不能代替正式结果。
6. 浏览器能完成这条路径、看日志、回查数值对应的 Run/源码/产物，并在刷新后恢复。首批不要求全部 PR09 页面重设计。
7. 真实 Pi 的工具事件、流输出、会话、模型和用量留证；未配置供应商时单列环境待验，不用假 Worker 替代该项。

## 已实现批次：批准正式运行并回查结果

固定验收条件：

1. 新 Python 研究源码不在随包宿主白名单中，使用固定 digest 的 Linux Docker 镜像、批准的 argv/数据与评估协议；服务预检不在 SQLite 写锁中执行。
2. 开发测试批准与正式 Run 批准分开；正式 Run 必须经过 prepare→用户批准→submit，未批准或已失效的来源不会启动。
3. Docker 运行返回稳定 handle，独立 supervisor 保存实际状态、stdout/stderr、退出码、指标及产物；退出 0 但缺必需文件不能显示完整。
4. 控制服务关闭后运行继续；supervisor 重启或提交结果丢失先查询同一容器，不重复启动。取消/超时只作用于已核对归属的容器。恢复后的不确定日志明确 incomplete。
5. 现有 trusted-example 回归保持原受信执行边界，并通过真实适配器运行；本批不新增远程后端或通用宿主 Shell。
6. 工作台用字段表单创建 Docker 实验；用户可批准、提交、选择历史 Run、分页切换 stdout/stderr、预览/下载原始产物，并按该 Run 的实际快照回查源码。浏览器实际验证桌面和窄屏，刷新后仍可回查。

开发只跑运行契约、适配器、监管、源码回查及对应 UI 的相关验证；集成后统一全量和收口审查。硬磁盘配额、GPU、远程调度、完整前端迁移及其他非阻断发现留在原计划。本批通过仍不代替独立科研审查与整条真实 Pi 工作台旅程。

本批结果：非白名单 Python 正式运行、控制服务关闭后继续、监管恢复不重复及原始产物归档均已实测。浏览器已完成表单创建、单独批准提交、一阶/二阶比较、历史 Run 选择、固定源码回查和刷新恢复；桌面与 390px 可操作。下载事件自动化等待超时，实际落盘未验证，单列为环境验收项。详见[批次记录](acceptance/flow-run/RESULTS.zh-CN.md)。

## 已验收批次：明确排队、容量与恢复的资源调度

固定验收条件（2026-09-28，实施前记录）：

1. 正式 Run 与开发 SandboxJob 共用持久计算队列和 CPU/RAM/槽位预留；共享同一 SQLite 的两个控制服务不能同时超配或重复领取。保留原默认一项正式运行＋一项开发测试的槽位行为，额外资源预算由用户显式配置，不自动扩权。
2. 本机 Docker 用真实 engine 身份归并 context 别名，并在启动/恢复前核对绑定。unknown 和租约过期不释放预留；目标 A 未知时，只要宿主和目标 B 仍有容量，B 可以推进。context 改指别的 engine 不能被当作旧容器已终止。
3. 排队、恢复与占用查询有 SQLite 定向索引和有界读取，不因大量终态历史反序列化全部队列。旧未终态记录保守迁移占用，旧清单/批准/Run 摘要保持不变；超额历史不被取消或遗忘。
4. Pi worker 槽位单独持久化，跨控制服务守住配置上限，同时尊重项目和团队上限。任务结果提交不等于进程退出；失联保留未知占位。过期回收在事务内复核租约，不能误回收刚续租的任务。尝试预算与 worker 槽位不混为一谈，不自动重试可能付费请求。
5. 工作台由服务端提供有效容量、占用/未知、队列原因与恢复状态；用户可显式调整预算，不能据此改写已批准的资源契约。CPU/RAM 数字是调度预算而非实时硬件空闲；Pi worker 上限不冒充模型 HTTP 并发或账单上限。
6. 用实际本机任务验证跨正式/开发的容量竞争、排队后推进及控制服务恢复；用独立进程/连接验证并发领取与旧代拒绝，保留大历史规模的查询计划及耗时证据。浏览器实际操作容量设置、查看等待、完成后释放与刷新恢复。
7. 开发只跑相关测试，集成后统一全量与独立审查；只修本批阻断、安全与兼容问题。模型 HTTP 请求级限流、全站 SSE/虚拟列表、硬磁盘配额、其他远程/GPU目标及 PR07 其余性能迁移保留后续，不能以本批代替全项完成。
