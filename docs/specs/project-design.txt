
项目暂定名为 **Pi Research**，目标是：

> **以 Pi 为唯一 Agent 执行内核，实现本项目的科研工作流、实验管理、工作台、计算接入和成果管理。**

验收以**固定项目版本的功能覆盖、交互行为和关键状态语义**为依据。模型生成的研究建议应另设科研任务评测。

本设计文档定义工作流要求；静态阅读不能替代实际运行验证。**M0 验收基线**须记录本项目提交、实际能力、检查结果和未覆盖范围。

# 一、确定功能边界与验收要求

## 1. 完整范围不只是设计实验和实验树

科研工作台 的公开定位包含本地优先、独立会话和工作区、实验快照、证据关联、自动研究，以及多种计算后端。

建议建立如下功能对齐清单。表中的“实现要求”是你的开发任务，不代表 Pi 已经提供这些能力。

| 功能域      | Pi Research 必须实现的内容                                     | 主要验收对象          |
| -------- | ------------------------------------------------------- | --------------- |
| 项目管理     | 新建、导入本地仓库、关联论文、项目设置、项目切换、移除项目                           | 项目生命周期、原始文件保留策略 |
| Agent 会话 | 新建、恢复、重命名、归档、流式输出、中断、消息排队、重试、对话分支                       | 会话历史和交互行为       |
| 科研交互     | 计划模式、问题确认、权限批准、方案修改后重新批准                                | 人工参与的完整闭环       |
| 工作区      | 会话隔离、文件浏览编辑、Git 状态、代码差异、终端                              | 并行工作不互相覆盖       |
| 文献研究     | 多源检索、关键词与语义检索、论文阅读、引用、原始图表证据                            | 检索来源、全文定位、证据有效性 |
| 实验设计     | 假设、对照、变量、指标、执行方案、审核与确认                                  | 方案可检查、可执行       |
| 论文复现     | 拆解论文主张、选择复现规模、逐项实验、记录差异、形成报告                            | 论文证据与实际观测分离     |
| 实验树      | 基线、派生节点、分轮探索、节点冻结、说明、树形与表格视图                            | 血缘和状态语义         |
| 实验执行     | 固定执行契约、不可变源码快照、提交、监控、取消、日志、恢复                           | 实际运行的代码与记录一致    |
| 自动研究     | 完成事件触发分析、修复、补充候选、晋级、停止                                  | 不丢事件、不重复执行      |
| 并行助手     | 独立会话、独立工作区、授权范围、完成回传、主会话唤醒                              | 委派边界和并发限制       |
| 证据与成果    | 日志引用、文件引用、图表、CSV、报告、产物浏览                                | 每个结论能追溯         |
| 论文写作     | LaTeX、模板、编译、错误定位、PDF 预览                                 | 真实文件与可编译成果      |
| 外部协作     | Git 发布、Overleaf 关联和同步、冲突处理                              | 授权、同步与失败恢复      |
| 计算管理     | 本地、SSH、Slurm、Kubernetes、Ray、HF Jobs、Modal、Tinker、自有托管计算 | 每个后端的真实作业测试     |
| 远程工作台    | 连接远程主机、打开远程项目、重连、切换运行环境                                 | 与“远程跑实验”分别验收    |
| 设置与分发    | 模型、凭据、计算默认值、技能、模板、数据目录、主题、语言、升级                         | 安装后完整可用         |

其中，并行助手、等待／唤醒、论文写作和可复用模板在原版文档里都有对应工作流；不能把它们当作“实验树做完后的可选装饰”。

原版前端还暴露了文件编辑冲突检测、对话分支、交互式计划确认和 Overleaf 同步等接口，因此只照着 README 开发会漏掉实际产品能力。

## 2. 有三处需要明确写进差异说明

**第一，原版的多 Agent 框架选择，替换成 Pi 内的模型和配置选择。**
你的要求是统一使用 Pi，因此不再启动 Claude Code、Codex 或其他框架。保留“每个会话可选不同模型和配置”的用户能力，但不宣称底层框架行为完全相同。

**第二，原版托管计算和账户服务，必须由自己的服务替代。**
只实现本地、SSH、Slurm，不等于全量复刻。完整目标还需要自己的账户、组织、计算供应商接入、资源目录、实例生命周期及用量管理。原版也区分本地功能和其服务拥有的组织、托管计算能力。

**第三，结构化实验协议、指标数据库、严格审批，是建议增强的内部实现。**
原版文档主要通过实验描述和运行日志表达科研信息。你可以用更强的数据结构实现相同用户能力，但不要把自己设计的 Schema 误认为原版现成接口。

# 二、总体技术路线：不改 Pi 内核，重建科研应用层

建议第一版采用：

| 层级           | 建议选择                 | 职责               |
| ------------ | -------------------- | ---------------- |
| 前端           | React＋TypeScript     | 工作台、聊天、实验树、文件和成果 |
| 控制服务         | Node.js＋TypeScript   | 业务规则、权限、任务、API   |
| Agent Worker | Pi SDK＋独立 Worker 进程  | 推理、研究、实现、分析      |
| 执行服务         | 独立 Runner Supervisor | 正式实验运行和恢复        |
| 本地存储         | SQLite＋文件产物库         | 本地优先的数据所有权       |
| 实验代码         | Git＋受控工作副本＋快照归档      | 血缘与复现            |
| 远程／团队版       | 可替换数据库和对象存储适配层       | 后续扩展，不改变领域接口     |

Pi 官方 SDK 支持嵌入 Node.js／Bun，提供会话、模型、工具和资源配置入口，因此适合放在独立 Worker 中使用。

建议工程结构如下：

```text
pi-research/
  apps/
    web/                       科研工作台
    server/                    科研控制服务
    agent-worker/              Pi 会话执行进程
    runner-supervisor/         计算作业监管进程
    cli/                       自己的命令行入口
    desktop/                   桌面应用包装

  packages/
    domain/                    项目、实验、运行、证据领域模型
    contracts/                 API、事件、工具 Schema
    storage/                   数据库和产物存储
    workspace/                 工作区、Git、快照
    pi-adapter/                Pi SDK 适配
    research-tools/            暴露给 Pi 的科研工具
    research-workflows/        研究、设计、复现、分析流程
    scheduler/                 队列、唤醒、租约、恢复
    literature/                文献来源与全文处理
    evidence/                  指标、引用、证据验证
    runners/                   各计算后端
    publications/              报告、LaTeX、发布、同步
    policy/                    授权、审批、预算
    ui-components/             工作台公共组件

  skills/                      自己编写的科研技能
  tests/
    parity/                    功能对齐测试
    integration/
    e2e/
    recovery/
    security/
    research-evals/

  docs/
    reference-baseline/
    architecture/
    acceptance/
```

**最重要的工程约束：前端、CLI 和 Pi 工具必须调用同一套业务服务。**

不能出现“前端创建实验走数据库，Agent 创建实验直接写 JSON，CLI 创建实验另走一套逻辑”的情况。

# 三、实施路线总览

不建议先承诺固定周数；应按下面的交付关卡推进。每阶段都可以演示和验收，后期功能不是删除，而是按依赖顺序补齐。

| 阶段 | 目标             | 主要依赖      | 阶段结束时必须成立         |
| -- | -------------- | --------- | ----------------- |
| M0 | 固定对标版本和验收规范    | 无         | 知道“要复刻什么、如何证明完成”  |
| M1 | 建立控制服务和领域模型    | M0        | 不接 Agent 也能管理业务对象 |
| M2 | 完成 Pi 会话与工具接入  | M1        | 会话可恢复，交互可中断和审批    |
| M3 | 打通实验树与本地运行     | M1，部分 M2  | 固定快照真实运行，结果可追溯    |
| M4 | 实现研究、设计和论文复现   | M2、M3     | 从问题到实验方案再到证据闭环    |
| M5 | 实现自动研究与并行委派    | M3、M4     | 事件驱动、并发可控、可恢复     |
| M6 | 完成工作台与成果系统     | M2—M5 的接口 | 主要用户旅程可在 UI 完成    |
| M7 | 补齐计算后端和远程工作台   | M3、M5     | 所有声明支持的后端通过实测     |
| M8 | 补齐协作、托管服务和安装分发 | M6、M7     | 达到完整产品范围          |
| M9 | 对齐验证、安全与稳定性验收  | 全部        | 功能矩阵全部有真实测试证据     |

前端可以从 M1 开始并行开发，但必须使用已定义的契约和测试数据，不能反过来用页面状态决定业务模型。

# 四、M0：先建立“功能复刻合同”

## 目标

把原版变成一个**可重复验证的参照物**，避免做了几个月之后才发现核心交互缺失。

## 具体任务

### M0-01：固定版本和运行条件

记录 科研工作台 的提交版本、Pi 的精确版本、操作系统、浏览器、模型配置和计算环境。

对标时不跟着 `main` 自动变化；上游新增功能进入后续差异清单。

### M0-02：录制完整用户旅程

至少覆盖：

| 用户旅程      | 必须记录的内容          |
| --------- | ---------------- |
| 新建项目并导入仓库 | 输入项、错误状态、目录变化    |
| 开始文献研究    | 检索过程、论文展示、引用点击   |
| 设计实验并批准   | 计划卡片、修改、批准后的行为   |
| 执行并分叉实验   | 树变化、Git 差异、日志和结果 |
| 自动研究      | 完成一个实验之后如何继续     |
| 并行委派      | 助手出现位置、权限、完成回传   |
| 写论文和同步    | 文件生成、编译错误、同步冲突   |
| 切换远程工作台   | 项目归属、连接状态、恢复行为   |

不仅记录正常路径，还要记录取消、失败、断网、刷新、关闭窗口和重新打开。

### M0-03：建立机器可读的对齐矩阵

建议每项功能记录：

```yaml
id: EXP-FREEZE-001
name: 有效结果产生后冻结实验源码
specification: docs/specs/project-design.txt
implementation:
  service: ExperimentService
  operation: recordOutcome
acceptance:
  - 有效结果形成后禁止覆盖原实验源码
  - 后续方案变化必须创建子实验
  - 实验说明仍允许追加研究记录
status: not_started
```

这里的字段是建议的项目管理格式，不是原版格式。

### M0-04：把差异分成三类

使用 `exact`、`equivalent`、`intentional-deviation`：

* `exact`：外部可见行为应一致，例如冻结、取消、恢复。
* `equivalent`：用户能力一致，内部实现不同，例如全部改用 Pi。
* `intentional-deviation`：明确改进的安全默认值或产品行为。

**验收门槛：每项功能都有对应用户旅程、后端操作和自动化用例；“看起来差不多”不算通过。**

# 五、M1：先把科研对象和控制服务建好

这一阶段先不依赖模型。使用普通 API 就应能够建立项目、实验、运行计划和证据关系。

## 1. 建立核心数据模型

建议分为四组，而不是一个巨大的 `research_session` 表。

| 数据组      | 核心对象                                                                      | 用途               |
| -------- | ------------------------------------------------------------------------- | ---------------- |
| 项目与执行上下文 | `Project`、`ResearchContract`、`Workspace`、`AgentSession`                   | 项目、固定执行契约、工作区、对话 |
| 科研过程     | `Hypothesis`、`Experiment`、`ExperimentRevision`、`ResearchRound`、`Campaign` | 假设、实验版本、研究轮次     |
| 计算执行     | `RunIntent`、`Run`、`RunAttempt`、`ComputeTarget`                            | 准备、实际运行、基础设施重试   |
| 证据与控制    | `Artifact`、`Evidence`、`Claim`、`Decision`、`Approval`、`Task`、`Event`        | 结论、授权、调度、恢复      |

必须明确以下区别：

**Experiment 是“研究什么”。Run 是“某个固定方案的一次运行”。Session 是“Agent 的对话上下文”。**

三者不能共用同一个 ID，也不能强制一一对应。

建议关系为：

```text
一个 Project
  包含多个 Experiment
  包含多个 AgentSession
  包含多个 ResearchRound

一个 Experiment
  对应一个主要父实验
  可以经历多个准备期 Revision
  可以包含多个 Run

一个 Run
  固定一个 RunManifest
  可以包含基础设施重试 Attempt

一个 AgentSession
  可以顺序处理多个实验任务
  通过 Task 与 Experiment / Run 关联
```

## 2. 定义状态，而不是只存一个 `status`

至少分开：

```text
实验生命周期：
provisional / frozen / archived

执行状态：
prepared / queued / submitting / running /
cancelling / succeeded / failed / cancelled / unknown

结果完整性：
pending / complete / incomplete / invalid

科研判断：
pending / supported / not_supported / inconclusive
```

例如，“进程成功退出但没产出评估指标”不能显示成“假设得到支持”。

## 3. 建立统一 API 和事件契约

API 按业务操作设计，例如：

```text
POST /projects
POST /sessions
POST /sessions/:id/messages
POST /sessions/:id/interrupt

POST /experiment-plans
POST /experiment-plans/:id/approve
POST /experiments/:id/children

POST /run-intents
POST /run-intents/:id/submit
POST /runs/:id/cancel

GET  /runs/:id/logs
GET  /projects/:id/experiment-tree
GET  /projects/:id/events
```

所有写操作都要携带或由服务端生成操作标识，用于重复请求去重。

需要防并发覆盖的操作携带 `expectedVersion`。错误不能只有字符串，至少区分：

```text
EXPERIMENT_FROZEN
WORKSPACE_BUSY
APPROVAL_REQUIRED
APPROVAL_STALE
BUDGET_EXCEEDED
FILE_VERSION_CONFLICT
RUN_ALREADY_SUBMITTED
PROVIDER_STATE_UNKNOWN
```

## 4. 建立持久化和安全底座

这一阶段就实现数据库迁移、事务、事件记录、操作审计、路径访问控制、凭据引用和备份恢复。

**验收门槛：关闭服务再启动，业务对象和未完成任务不丢失；重复发送同一请求不会创建重复实验或重复运行。**

# 六、M2：把 Pi 改造成可嵌入的科研执行器

这里的“改造”主要发生在 `pi-adapter` 和自定义工具，不是 fork Pi。

## 1. 封装 Pi，禁止业务代码直接到处调用 SDK

建立自己的 `ResearchAgentRuntime`，负责会话创建、恢复、提示、事件订阅、中断和销毁。

Pi 官方已经提供创建和打开指定持久化会话的方式。多项目应用应保存明确的 Session 文件位置，不能靠“继续最近一个会话”猜测恢复目标。

建议宿主数据库保存：

```text
sessionId
projectId
workspaceId
piSessionPath
modelConfiguration
resourceBundleVersion
activeTaskId
leaseOwner
leaseExpiresAt
```

同一 Session 只允许一个 Worker 写入。

## 2. 完整实现聊天交互

不能只实现 `prompt()` 和文本流，还需要：

**发送与排队。** 用户在执行期间发送消息，明确选择“引导当前任务”或“后续执行”。

**中断与恢复。** 中断 Agent 和取消正式实验是不同操作，界面应明确区分。

**重试与分支。** 重试回答、编辑旧消息、切换对话分支，不应偷偷撤销实验数据库或回滚正式运行。

**附件与引用。** 上传的图片、论文和文件进入受控存储，消息只保存稳定引用。

**运行事件。** 前端使用完成后的消息作为权威展示结果，不把断开的流误判为任务失败。

Pi 的 `agent_end` 是低层执行结束，后面仍可能继续自动恢复或处理排队工作；宿主判断 Pi 已不再自动继续时，应关注 `agent_settled`。它仍不代表训练实验已完成。

## 3. 实现计划、权限、提问三种交互

建议建立统一的 `InteractionRequest`：

```text
kind: plan | permission | question
sessionId
taskId
payload
status
expiresAt
approvedScope
```

审批必须绑定具体方案版本、运行清单、计算目标和额度。

**用户批准之后，Agent 修改了关键代码、预算或执行目标，旧批准应失效。**

不要在 Worker 内部用一个无限等待的 Promise 保存审批状态。审批请求需要落库，进程重启后仍可继续处理。

## 4. 实现自己的科研工具

工具按阶段开放：

```text
研究：
literature_search / paper_read / evidence_register

设计：
hypothesis_submit / experiment_plan_submit / approval_request

实验：
experiment_get / experiment_branch / experiment_diff

执行：
run_prepare / run_submit / run_inspect / run_cancel / run_logs

分析：
metrics_query / compare_runs / decision_submit

委派：
agent_delegate / task_inspect

成果：
artifact_register / paper_compile / publication_prepare
```

每个工具都应完成 Schema 校验、权限检查、幂等控制和审计。

Pi 扩展支持注册自定义工具和监听事件，可以通过资源加载器注入自己的扩展实现。

## 5. 控制资源加载和命令权限

只加载审核过的技能、提示词和扩展；不能因为一个研究仓库包含 `.pi` 文件，就自动信任其中的可执行扩展。

Pi 默认没有内置的文件、进程、网络和凭据权限限制，必须由宿主系统建立隔离。([GitHub][2])

**验收门槛：Pi 能创建研究方案、请求批准、执行授权工具；重启后能恢复；越权请求由服务端拒绝，而不是只收到提示词警告。**

# 七、M3：实现实验树、版本冻结和本地 Runner

这是项目最重要的一阶段。这里不可靠，后面自动研究越强，破坏越大。

## 1. 工作区按 Session 隔离，实验按版本保存

建议每个可写 Session 分配独立工作区，实验节点保存独立的分支和快照引用。

同一个 Session 可以先后负责多个实验，但一个实验分支同一时刻只能有一个写入者。

不要把工作区路径当作实验结果的永久来源。工作区会继续变化，正式结果必须引用不可变快照。

## 2. 实现原版的固定运行契约

科研工作台 的科研规则要求同一实验树继承固定的运行命令和环境，实验变化通过提交后的代码或配置表达，而不是临时更改命令行参数或环境变量。

建议增加 `ResearchContract`：

```text
固定入口命令
工作目录规则
非敏感环境配置版本
依赖与镜像约束
数据集和切分版本
评估协议版本
指标定义
输出约定
```

例如，学习率从 `1e-4` 改成 `3e-4`，应修改配置文件并创建相应实验变体，不能只在提交作业时临时传入另一个参数。

随机种子的重复计划同样写入已提交配置，由固定入口执行，不用临时环境变量绕开追踪。

改变运行契约时，创建新的契约版本和明确的比较边界；不能直接覆盖历史实验的执行条件。

## 3. 实现不可变 `RunManifest`

每次提交至少保存：

```text
experimentId / experimentRevisionId
researchContractId
sourceCommit
sourceArchiveDigest
configDigest
datasetVersion
evaluationProtocolVersion
environmentImageDigest
dependencyLockDigest
computeTargetId
resourceSpecification
credentialReferences
expectedArtifacts
approvalId
```

不要把密钥写进清单；保存凭据引用和版本。

源码归档必须显式处理未跟踪文件、子模块、Git LFS 和外部依赖。不能一边说“完整快照”，一边遗漏真正运行所需的文件。

运行步骤应为：

```text
检查工作区
→ 固化源码与配置
→ 生成归档和运行清单
→ 验证批准仍有效
→ 保存 RunIntent
→ 提交 Runner
→ 保存外部 Job 标识
→ 采集日志和产物
→ 形成结果证据
```

## 4. 实现“可修复”和“已回答”边界

原版区分尚未回答问题的临时节点和已经产生研究结果的冻结节点：前者可原地修复，后者必须派生子节点。差结果也属于结果；但普通依赖错误不一定回答了研究问题。

服务端应执行：

| 情况                | 允许的后续操作            |
| ----------------- | ------------------ |
| 缺失依赖，实验没有真正开始     | 同一节点修复，创建新的运行记录    |
| 基础设施故障，源码不变       | 同一固定清单进行执行重试       |
| 获得预期指标，但效果变差      | 冻结节点，后续变化创建子实验     |
| 得到与假设相关的 OOM／超时结果 | 保留为研究结果，不机械地当作无效失败 |
| 结果是否回答问题尚不明确      | 暂停修改，进入审核状态        |

冻结主要保护源码和实验定义。研究备注可以继续追加，但不能改写旧的日志和证据。

## 5. 本地 Runner 先完成全部执行语义

至少包含启动、检查、日志读取、取消、资源限制、产物收集、异常退出和重启恢复。

训练进程不应成为 HTTP 请求的子生命周期，也不应依赖 Pi 会话持续在线。

**验收门槛：实验启动后修改工作区，运行中的代码不变；停止 Pi 不导致正式运行丢失；旧结果始终能定位到实际执行快照。**

# 八、M4：实现文献研究、实验设计和论文复现

这三个工作流需要分别开发，不要用一个通用“科研提示词”代替。

## 1. 文献研究工作流

建议流程：

```text
解析研究问题
→ 选择文献来源
→ 初步检索
→ 去重与候选排序
→ 针对缺口继续检索
→ 阅读关键论文
→ 提取主张、方法和限制
→ 保存证据
→ 形成研究综述
```

原版包含 alphaXiv、OpenAlex、bioRxiv 和 PubMed 相关检索，并要求对选中的论文进一步阅读后再进行主张级引用。它还区分关键词、语义检索和日期等控制。

你的实现应采用独立的 `LiteratureProvider` 接口；可以直接接公开服务，但不得通过 外部科研运行时 转发。

证据记录至少包括论文标识、版本、获取时间、全文内容版本、章节／页码／段落定位、原文片段和关联主张。

论文图表需要保存原始来源和裁剪定位；用户能从综述回到原始证据。

检索失败时保留其他成功来源的结果，不把“某个接口失败”解释成“没有相关论文”。

## 2. 实验设计工作流

建议让 Pi 输出结构化方案，字段至少覆盖：

| 类别   | 内容              |
| ---- | --------------- |
| 研究目标 | 问题、假设、预期机制      |
| 证据依据 | 相关论文和已有实验       |
| 设计   | 对照、干预因素、控制因素    |
| 数据   | 数据版本、切分、预处理     |
| 评估   | 主指标、保护性指标、评估协议  |
| 重复   | 随机种子计划及其依据      |
| 判断   | 成功标准、无结论条件、停止规则 |
| 执行   | 代码修改范围、资源要求、风险  |

流程为：

```text
生成草案
→ 程序校验
→ 科研审核
→ 用户修改或批准
→ 固化方案版本
→ 创建实验节点
→ 分配实现任务
```

Reviewer 负责提出问题，服务端负责真正的约束。Reviewer 的“通过”不能替代预算和权限检查。

## 3. 论文复现工作流

单独实现 `reproduce-paper`：

```text
识别论文
→ 拆解主要经验性主张
→ 提取原始实验条件
→ 匹配可用计算资源
→ 选择完整或缩小规模的复现方案
→ 创建基线和变体
→ 执行并比较
→ 形成逐主张复现报告
```

每个主张都记录“论文报告值、实际观测值、规模差异、方法替代、证据、尚未尝试内容”。

原版也包含专门的论文复现工作流，并区分本地报告和经过授权的 Git 发布成果。

**验收门槛：拿一个小型公开研究任务，能从论文或问题开始形成方案、运行实验，并生成所有数字都有证据来源的报告。**

# 九、M5：实现真正可恢复的自动研究

自动研究的核心是**持久化状态机和事件处理**，不是让 Pi 在一个超长对话里不断调用 Shell。

## 1. 增加 Campaign 和 ResearchRound

`Campaign` 表达一次持续研究活动：

```text
研究目标
当前关注实验
运行契约
当前研究轮次
资源与时间约束
自动执行权限
已处理结果集合
停止策略
```

`ResearchRound` 表达同一个决策下的一组候选方案。

原版强调同一轮的候选在共同父节点下展开，下一轮建立在前一轮保留的结果上，而不是把所有实验永远挂在根节点下。

## 2. 实现四类决策

| 决策      | 业务含义          | 服务端动作           |
| ------- | ------------- | --------------- |
| Repair  | 当前运行没有回答实验问题  | 检查修复次数，授权原节点修复  |
| Refill  | 继续当前轮候选探索     | 释放资源后补充下一个候选    |
| Promote | 保留当前结果作为下一轮基础 | 更新当前关注父节点，创建新轮次 |
| Stop    | 目标达成或当前方向结束   | 停止新增任务，保存总结和原因  |

这四类决定应作为结构化 `Decision` 保存，而不是只写在聊天里。

原版的自动研究流程使用这四类动作，并要求每次完成后读取实际运行证据再决定下一步。

## 3. 按完成事件推进，不等待整批结束

实现：

```text
run.completed
→ 结果采集任务
→ 证据校验任务
→ Pi 分析任务
→ Decision 校验
→ 继续、派生或停止
```

每次唤醒都重新对账数据库，处理所有尚未处理的终态运行，而不是只处理当前消息里提到的一个 Run。

原版文档也明确区分“等待变化的信号”和运行状态的真实来源；不能把一次唤醒当作完整结果集合。

## 4. 加入有界探索策略

建议兼容配置中提供：

```yaml
maxUnansweredRunsPerNode: 2
maxConsecutiveRegressions: 3
maxDelegationDepth: 1
maxConcurrentAgents: configurable
maxConcurrentRuns: configurable
maxTotalGpus: configurable
deadline: optional
```

其中，无结果修复限制、连续退步停止和委派层级分别参考原版工作流；具体预算和审批阈值由你的产品策略确定，不当作普适科研定律。

资源调度按 GPU、CPU、内存等实际需求计数，不能把“最多四个任务”误认为“最多四张 GPU”。

## 5. 实现并行助手

助手需要独立简报、Session、工作区、工具权限和完成标准。

主会话收到结果后应检查成果，不自动合并代码；助手不应无限递归生成助手。原版也要求助手有独立上下文、明确分支归属和计算授权。

**验收门槛：两个实验先后完成，其中一个完成时系统正在分析另一个，仍不会漏处理；重启后不会重复派生或重复提交。**

# 十、M6：补齐工作台、证据查看和科研成果

## 1. 工作台不是一个聊天页面

至少实现以下产品表面：

| 表面     | 关键交互                 |
| ------ | -------------------- |
| 项目首页   | 项目列表、活动状态、创建和移除      |
| 会话面板   | 历史、模型、队列、批准、附件、分支    |
| 实验树／表格 | 选择、搜索、折叠、状态过滤、派生、比较  |
| 实验详情   | 方案、说明、代码差异、运行列表、证据   |
| 代码工作区  | 文件树、编辑、冲突提醒、终端、只读快照  |
| 成果区域   | 报告、图片、表格、论文、产物目录     |
| 设置区域   | 模型、计算、凭据、技能、模板、存储、更新 |

原版组件中已经存在实验树、实验表格、工作区、代码、终端、产物、技能和文件查看等独立表面。

布局、尺寸、快捷键和标签页行为依据 M0 的实测基线实现，不凭印象猜测原版位置。

## 2. 实验树的实现要求

建议使用标准 JSON 节点／边模型作为数据源，React Flow 展示，ELK 做自动布局；官方已有对应集成示例。([React Flow][3])

必须做到：

**布局和血缘分开。** 拖动节点只改变位置，不能悄悄改变父实验。

**选择状态联动。** 树、表格、详情和会话引用使用同一个实验标识。

**状态可解释。** 区分运行失败、指标无效和假设未得到支持。

**可替代操作。** 键盘和列表视图可以完成关键操作，不能只能靠悬浮卡片。

**刷新恢复。** 保存选中节点、视口、折叠状态和已打开标签页。

## 3. 实现类型化证据引用

建议内部使用如下概念：

```text
PaperEvidence：论文版本＋页码／段落
CodeEvidence：快照＋路径＋行号
RunEvidence：运行＋日志字节范围
ArtifactEvidence：产物版本＋内容哈希
```

聊天和报告中的可点击引用由这些对象生成，不直接信任模型编造的本地路径。

原版要求聊天中的代码、运行结果和产物使用可点击引用，并明确要求读取运行日志后再报告测量结果。

## 4. 报告和论文系统

报告产物保存正文、图表、数据与生成脚本之间的关系。

LaTeX 模块实现模板选择、源码编辑、编译、日志定位、PDF 预览和重新编译；编译进程同样需要隔离。

原版区分报告产物和工作树中的 LaTeX 论文，并要求写出实际文件而非仅在聊天中给提纲。

**验收门槛：用户点击报告中的指标、代码或图表，能打开对应版本；文件移动、会话切换和刷新不会让引用悄悄指向另一份内容。**

# 十一、M7：补齐所有计算后端，以及远程工作台

## 1. 先统一执行器契约

建议每个 Runner 实现：

```typescript
interface RunnerAdapter {
  preflight(target: ComputeTarget): Promise<PreflightResult>;

  submit(
    intent: PreparedRunIntent,
  ): Promise<SubmissionResult>;

  inspect(handle: JobHandle): Promise<JobObservation>;

  cancel(handle: JobHandle): Promise<CancelResult>;

  readLogs(
    handle: JobHandle,
    cursor: LogCursor,
  ): Promise<LogChunk>;

  collectArtifacts(
    handle: JobHandle,
  ): Promise<ArtifactManifest>;

  reconcile(
    intent: PreparedRunIntent,
  ): Promise<ReconcileResult>;
}
```

这是建议的应用接口，不是 Pi SDK API。

特别需要 `reconcile`：提交请求已经到达计算平台，但宿主未收到响应时，必须先查证，不能直接重提。

## 2. 按后端分别实现和验收

原版计算技能列出了本地、SSH、Slurm、Kubernetes、Ray、Hugging Face Jobs、Modal、Tinker 和 科研工作台 托管计算。

| 后端         | 开发重点                   | 必须测试的特殊问题      |
| ---------- | ---------------------- | -------------- |
| 本地         | 进程／容器监管、资源限制           | 应用退出后作业归属      |
| SSH        | 传输快照、远程监管、日志回传         | 网络断开不等于作业失败    |
| Slurm      | 提交脚本、外部 Job ID、排队和资源映射 | 排队、抢占、取消与最终状态  |
| Kubernetes | Job、镜像、数据和产物挂载         | Pod 重建与结果只收集一次 |
| Ray        | 作业提交、环境和工作目录打包         | 任务失败与集群状态区分    |
| HF Jobs    | 凭据、镜像／资源规格、日志和结果       | 容量不足、作业超时      |
| Modal      | 执行包装、快照分发、产物存储         | 远程函数结束与产物收集    |
| Tinker     | 本地控制器、远程模型操作、检查点       | 停控制器不等于撤销已接受请求 |
| 自有托管计算     | 供应商适配、资源目录、账户与用量       | 创建失败、重复计费、孤儿实例 |

Tinker 尤其不能用统一“取消成功”掩盖语义：原版文档说明取消停止的是本地控制器，已经被远程服务接受的请求仍可能完成。

每个后端应发布能力清单，例如是否支持 GPU、真实远程取消、检查点恢复、交互终端和产物回传。无法支持的能力要明确返回，而不是模拟成功。

## 3. 远程工作台单独实现

区分：

**模式 A：本地控制、远程计算。**
业务数据库和 Pi 在本地，正式实验在远程执行。

**模式 B：远程完整工作台。**
数据库、Pi、工作区和 Runner 在远程，用户通过本地浏览器访问。

模式 B 需要远程服务安装／版本检测、连接授权、隧道、重连、运行环境标识、项目作用域和停机确认。

不能因用户断开浏览器就停止远程实验。

**验收门槛：每个声明支持的后端都完成真实提交、读取日志、收集结果、取消和断线恢复测试。只有 Mock 测试不算后端支持完成。**

# 十二、M8：协作、托管服务、设置和安装分发

这一阶段用来补齐“产品完整性”，不是只做包装。

## 1. Git 发布与成果发布

将发布设计为显式事务：

```text
准备发布内容
→ 检查敏感文件和历史
→ 展示目标仓库与可见性
→ 用户确认
→ 发布
→ 验证链接
→ 保存发布记录
```

实验代码与报告发布可以分开，禁止为发布报告覆盖已冻结的实验分支。

自包含报告或教学 Notebook 应使用已经产生的证据，不要求读者先重新执行昂贵训练。

## 2. Overleaf

分别实现并验收：

**项目关联。** 保存本地论文与远程项目的映射，验证当前账户是否可访问。

**双向同步。** 记录同步基点，识别双方修改，提供保留本地／采用远程等冲突解决。

**实时通道。** 单独验证连接、重连、断线和版本冲突，不把 Git 同步冒充实时编辑。

外部账户能力或服务协议不满足时，显示明确的不支持状态；不能悄悄切换成另一种行为。

## 3. 自有托管计算服务

完整复刻范围下还需建设：

```text
账户与组织
凭据管理
计算供应商适配
GPU / CPU 资源目录
实例申请与释放
作业与独立实例的区分
资源授权与用量记录
孤儿实例清理
故障和容量不足处理
```

原版独立实例用于持久机器和手工工作，与实验作业不是同一个对象。你的系统也应分别建模。

## 4. 设置与分发

完成技能／模板导入管理、主题与语言、计算默认值、数据目录迁移、CLI、桌面安装、升级和回滚。

原版设置组件涉及这些模型、计算、存储和更新入口，不能在完整对齐时只留下一个 API Key 输入框。

数据目录迁移需要阻止新写入、校验空间、迁移文件、核对完整性、切换配置并提供失败回滚。

**验收门槛：在干净机器上安装，从配置模型开始完成研究闭环；升级后旧项目、Session、运行证据仍可打开。**

# 十三、M9：用什么标准证明复刻完成

## 1. 核心行为验收

建议把以下场景做成必须通过的自动化测试：

| 编号  | 场景                | 通过条件              |
| --- | ----------------- | ----------------- |
| T01 | 重复点击提交运行          | 同一提交意图不会生成重复作业    |
| T02 | 作业提交后服务崩溃         | 恢复时对账，不盲目重提       |
| T03 | 运行中修改工作区          | 已启动实验仍使用原快照       |
| T04 | 已有结果的节点被修改        | 服务端拒绝，要求创建子实验     |
| T05 | 缺失依赖导致无结果         | 允许原节点修复，保留失败记录    |
| T06 | 两个 Worker 写同一分支   | 一个获得写权，另一个明确等待或失败 |
| T07 | 多个运行近乎同时完成        | 所有结果恰好进入一次业务处理    |
| T08 | 用户消息与自动唤醒同时到达     | 顺序符合策略，唤醒不丢失      |
| T09 | 编辑旧聊天消息           | 不隐式回滚实验和运行        |
| T10 | Agent 中断          | 正式运行不会被错误标成取消     |
| T11 | 取消请求与作业完成竞争       | 保留真实最终状态          |
| T12 | 文件被用户和 Agent 同时修改 | 显示冲突，不静默覆盖        |
| T13 | 报告包含不存在的运行引用      | 验证失败，不发布为有效证据     |
| T14 | 修改已批准方案           | 旧批准失效             |
| T15 | SSH 断线后恢复         | 能重新识别原 Job 和日志位置  |
| T16 | Overleaf 双方修改     | 出现可处理冲突，不覆盖一方     |
| T17 | 数据目录迁移中断          | 可恢复或回滚，原数据可用      |
| T18 | 环境完全没有 外部科研运行时        | 全部核心功能仍能运行        |

## 2. 故障注入测试

在以下位置主动杀掉进程或切断网络：

```text
保存提交意图之后、真正提交之前
计算平台接受请求之后、返回 Job ID 之前
采集部分日志之后
产物上传之后、数据库登记之前
用户批准之后、执行之前
结果完成之后、分析任务创建之前
分支创建之后、实验对象提交之前
```

要用这些测试证明恢复机制，而不是只做一次“重启看起来没问题”。

事件系统采用“允许重复投递、业务处理幂等”的原则，不承诺外部计算服务天然具备严格的恰好执行一次。

## 3. 安全测试

至少验证路径穿越、恶意压缩包、符号链接越界、HTML／SVG 预览注入、凭据泄露、越权项目访问、提示注入和计算授权绕过。

尤其注意：只把部分工具放进沙箱，不会自动限制仍在宿主机执行的扩展；Pi 官方隔离文档明确说明了这一点。

## 4. 交互与视觉对齐

M0 生成基准截图和交互脚本，后续自动比较。

Playwright 支持截图比较，但浏览器、操作系统等环境差异会影响渲染，因此基准与测试环境需要固定。([Playwright][4])

不仅比较首页，还要比较加载、失败、审批、空树、大树、长日志、文件冲突和远程断线状态。

## 5. 科研能力评测

分开两套评测：

**确定性产品测试。** 使用固定 Agent 响应和固定任务，检查业务状态与恢复行为。

**真实 Pi 科研测试。** 使用小规模真实任务，检查是否理解论文、设计合理对照、正确运行、发现失败、引用证据并形成适度结论。

评估重点应是：

```text
任务是否完成
正式运行是否可追溯
结论引用是否真实存在
是否混淆未测量结果与已测量结果
是否遵守执行预算与权限
失败后是否采取正确动作
```

不能把“生成了很长的研究报告”当作科研能力达标。

# 十四、团队分工与最先落地的代码

## 1. 按五条工作线组织

| 工作线      | 负责内容                |
| -------- | ------------------- |
| 核心后端     | 领域模型、状态机、API、数据库、审批 |
| Pi 与科研流程 | 会话适配、工具、技能、研究与分析评测  |
| 执行与基础设施  | 工作区、快照、Runner、恢复、隔离 |
| 前端与成果    | 工作台、实验树、文件、论文、证据展示  |
| 对齐与质量    | 原版基线、E2E、故障注入、发布验证  |

人数少时可以一人承担多条线，但接口和职责仍应分开。

**关键依赖是：领域契约 → 实验执行 → 自动研究。**
自动研究不能先于可靠的运行底座完成；漂亮的实验树也不能代替实验状态机。

## 2. 建议最先合并的八个 PR

| PR     | 内容                         | 合并条件         |
| ------ | -------------------------- | ------------ |
| PR-001 | 对标基线、功能矩阵、验收用例骨架           | 范围与差异分类明确    |
| PR-002 | 领域模型、迁移、统一错误和事件 Schema     | 基础状态测试通过     |
| PR-003 | 项目导入、工作区、分支写锁              | 并发写入不覆盖      |
| PR-004 | 源码归档、RunManifest、本地 Runner | 快照运行可追溯      |
| PR-005 | Pi 会话创建、恢复、流式事件和中断         | 重启恢复测试通过     |
| PR-006 | 科研工具、计划与审批                 | 未批准不能正式执行    |
| PR-007 | 实验树 API、树形 UI、运行详情         | UI 与数据库一致    |
| PR-008 | 第一条完整科研闭环                  | 从问题到报告全程独立运行 |

PR-008 的具体演示应当是：

> 导入一个小型实验仓库 → Pi 理解任务 → 提出并确认实验方案 → 建立基线 → 派生两个变体 → 真实运行 → 检查日志和指标 → 形成比较 → 从保留的结果继续创建下一轮子实验 → 输出带证据的报告。

这条闭环打通后，再扩展文献来源、计算后端、论文协作和桌面分发，而不是同时铺开几十项半成品。

## 最终交付定义

项目完成时，应该同时交付**应用、功能对齐矩阵、自动化测试、真实后端测试记录、科研任务评测报告、安装包和迁移文档**。

判断标准不是“界面像 科研工作台”，而是：

> **用户能完成同样的科研任务；每个实验和结论可追溯；中断后能恢复；所有声明支持的功能都有测试证据；整个系统在完全没有 外部科研运行时 的环境中独立运行。**

你的第一优先级应当是 **M0 的对齐合同、M1 的领域模型、M3 的快照执行链路**。这三部分做对，再把 Pi 接到受控工具上，后续的设计实验、自动研究和实验树才会成为同一个可靠产品，而不是几块彼此脱节的功能。
